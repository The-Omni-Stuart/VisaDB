# VisaDB

Machine-readable visa, transit, and travel-permit data for every passport ×
every destination — the dataset behind the Visa Vole app.

VisaDB is a fork of [xpressmike/visa-matrix](https://github.com/xpressmike/visa-matrix),

## What it is

203 passports × 202 destinations = **40,804 corridors**, each recording *where
its value came from* and *whether an independent source agrees* — not a single
number copied from one aggregator and hoped to be right:

```json
"VN": {
  "type": "visa-free",
  "days": 30,
  "source": "wikipedia",
  "checked": "2026-07-20",
  "confidence": "disputed",
  "dispute": { "wikipedia": "visa-free", "passport-index": "e-visa" }
}
```

When sources disagree, the cell says so instead of silently picking a winner.

Beyond the entry matrix, VisaDB models the two things a bare passport-vs-
destination grid can't:

- **Transit** — can you *transit* a country airside, which is independent of
  whether you can *enter* it (a visa-free entry does not always mean a visa-free
  airside connection, and vice versa).
- **Permits** — what a *foreign* travel document you also hold (a US green card, a
  Schengen residence card, an APEC Business Travel Card…) unlocks on top of your
  passport.

The canonical form is a SQLite database with all three axes in one file; a nested
JSON mirror is written alongside it so changes show up as a readable diff.

## Data model

`data/visa_data.db` has six tables:

| Table | Contents |
|---|---|
| `meta` | dataset name, version, build date, source notes |
| `countries` | ISO2 → name + region (203) |
| `visa_rules` | one row per corridor (40,804): entry `type` / `days` / `confidence` / `source` / `checked`, the `dispute` claims, and the transit axis (`transit` + `transit_note`) |
| `corrections` | manual overrides applied after the scrape (policy changes the sources still lag) |
| `visa_holdings` | the 13 foreign travel documents the permit layer models |
| `visa_benefits` | one row per (holding, destination): what that document grants there (223) |

`data/visa_data.json` is the same data as a nested grid — matrix cells carry both
the entry status and the transit axis, with `countries` / `corrections` /
`holdings` / `benefits` as top-level lists — so a change is a readable text diff.

### Files

| File | Role |
|---|---|
| `data/visa_data.db` | **canonical** — SQLite form the app consumes (all axes, one file) |
| `data/visa_data.json` | **canonical** — nested text mirror of the DB, for diffing / inspection |
| `data/visa-matrix-iso2.csv`, `data/visa-matrix-tidy.csv` | opt-in exports (`build.py --export`); lossy entry-grid convenience views |
| `data/countries-iso2.json`, `data/demonyms-iso2.json` | inputs: country / demonym → ISO2 maps used to join the sources |
| `data/overrides.json` | manual corrections applied after the scrape |
| `data/limited-recognition.json` | hand-curated rules for states with limited recognition (their Wikipedia pages are stubs, not matrices) |
| `data/transit.json` | curated, cited transit rules (policies + overrides) merged after the scrape |
| `data/visa-benefits.json` | the permit layer (generated by `gen_benefits.py`) |
| `build.py`, `gen_benefits.py` | stdlib-only build + permit-layer generator |

The DB and JSON are the committed product and are never gitignored. The CSV
exports are generated on demand and are gitignored.

### Entry status vocabulary

`visa-free` · `freedom-of-movement` · `eta` (electronic travel authorisation: ESTA,
eTA, K-ETA…) · `visa-on-arrival` · `e-visa` · `visa-required` · `refused`.

Confidence: `high` (sources agree — an ETA is treated as compatible with a bare
"visa free" claim, since sources label that regime either way) · `medium` (single
source) · `disputed` (sources disagree — both claims shown in `dispute`).

`days` is the stay granted on entry, present only for regimes that grant entry up
front (`visa-free`, `eta`, `visa-on-arrival`, `e-visa`, `freedom-of-movement`) and
never exceeding a year — source prose mixes stay length with visa validity and age
limits, and those parse into nonsense. `days_source` appears when the count came
from the cross-check source rather than the primary one.

### Transit

Transit is a **separate axis** from entry: `visa_rules` carries `transit`
(`free` | `required` | `conditional` | `unknown`) and a `transit_note`.

The base rule is *computed*, not stored: transit is `free` wherever entry is
`visa-free` or `freedom-of-movement` (airside transit is strictly less privileged
than entry — if you can enter without a visa, you can stay in the international
transit area). Every other corridor starts `unknown` and is filled from the
curated, cited overlay `data/transit.json` (37 policies + 12 explicit corridor
overrides), the same pattern as `limited-recognition.json`. The result: most
corridors end `free`, a small set are `required`, a few are `conditional`, and the
rest remain `unknown`.

- **`required`** — a transit visa is needed even for an airside connection (the
  high-value safety case).
- **`free`** — no transit visa despite a non-visa-free entry requirement (e.g. the
  Schengen airside transit privilege, the UK DATV exemption, the US C-1 / ESTA split).
- **`conditional`** — transit is permitted but only with booked, legally-approved
  onward travel to a third country (e.g. China 24 h / 240 h TWOV).
- **`unknown`** — no documented airside transit rule.

### Visa & residency holdings (permit layer)

A passport is not the only travel document that changes what you can enter. If you
hold a foreign visa or residence permit — a US green card, a Schengen residence
card, a UK BRP, an APEC Business Travel Card, GCC residence, etc. — several
destinations let you in on that alone, or relax the rule your bare passport would
get.

- `visa_holdings` — the 13 holdings (`us-green-card`, `us-visa`, `schengen-visa`,
  `schengen-residence`, `uk-visa`, `ca-pr`, `ca-visa`, `au-pr`, `uae-residence`,
  `jp-visa`, `gcc-residence`, `sg-visa`, `apec-card`), each with a `category`
  (residency / short_term_visa / long_term_visa / special_permit) and
  `issuing_country`.
- `visa_benefits` — one row per (holding, destination): `type`, `days`,
  `confidence`, `source`, `checked`, a `note` with the Wikipedia quote that backs
  it, and `source_page` + `source_url` — the destination's own "Visa policy of X"
  Wikipedia page (the 29 Schengen states plus Cyprus share the single "Visa policy
  of the Schengen Area" page) — so any row re-verifies with one click.

The holdings were seeded from the Passport Power Index visa-checker's list (250
entries) and **verified against the destination's own Wikipedia row** before being
kept: a note in another country's row (e.g. the "US citizens" row) is that other
country's policy, not the destination's, so an entry is only `confidence: "high"`
when the destination's row documents it. That check dropped ~27 VisaCheck entries
(wrong direction, non-matrix territories, duplicates) and corrected the rest.

Two things to remember:

- **A benefit only relaxes the underlying passport rule.** It never waives the need
  for a valid passport or the destination's normal admissibility checks (proof of
  funds, onward ticket, etc.).
- **The app still merges.** Each benefit is re-merged against the traveller's
  passport result and the better outcome wins — a green card can't make a `refused`
  corridor enterable.

The app's best-of merge (passport + holdings + transit) is specified in
[docs/app-merge-logic.md](docs/app-merge-logic.md).

`data/visa-benefits.json` is produced by `gen_benefits.py` (stdlib only); the
curated holdings/benefits live in that script as the single source of truth.
`build.py` loads it into the two tables.

## Passports covered

All of them. Passports with an English Wikipedia
["Visa requirements for X citizens"](https://en.wikipedia.org/wiki/Category:Visa_requirements_by_nationality)
page (~180) get Wikipedia as the primary source with passport-index as the
cross-check; the rest are covered by passport-index alone (and read
`"source": "passport-index", "confidence": "medium"` until a second source confirms
them).

States with **limited recognition** (Abkhazia, South Ossetia, Transnistria, Northern
Cyprus) are carried as both passports and destinations, and the SADR passport as a
passport only — none has a full Wikipedia visa matrix, so their rules are
hand-curated in `data/limited-recognition.json` and merged after the scrape. A de
facto passport is `refused` where it is not accepted as a travel document (the app
shows this grey); accepted-but-undocumented regimes are marked assumed
`visa-required`. All such cells are single-source (Wikipedia),
`confidence: "medium"`.

## Sources

- **Primary:** English Wikipedia visa-requirements pages — community-maintained,
  cited per row (mostly Timatic and government pages), quick to reflect rule
  changes, and carrying machine-readable day counts.
- **Cross-check / fallback:** [imorte/passport-index-data](https://github.com/imorte/passport-index-data),
  scraped from [passportindex.org](https://www.passportindex.org).
- Country/demonym resolution: [mledoze/countries](https://github.com/mledoze/countries).

## Rebuild

```sh
python3 gen_benefits.py        # regenerate data/visa-benefits.json (stdlib only)
python3 build.py               # scrape, merge, write visa_data.db + visa_data.json
python3 build.py --export all  # …also the opt-in CSV exports
```

Stdlib only, no dependencies. A weekly GitHub workflow re-runs the build and opens
a pull request whenever `data/` changes, so drift lands as a reviewable diff (and
disputes get a human look) rather than a silent push.

## What this is not

**Not legal advice and not an authority.** Visa rules change without notice and
depend on your specific circumstances. Always verify with the destination's
official government source before booking anything.
